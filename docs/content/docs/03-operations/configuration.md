## Manager (`conf/manager.toml`)

```toml
# Public plugin-marketplace URL linked from the Dashboard's YAML editor.
# Override for internal-mirror or air-gapped deployments (env: BUZ_MARKETPLACE_URL).
# marketplace_url = "https://plugins.example.com"

[server]
host = "0.0.0.0"
port = 8080
# tls_cert = "certs/cert.pem"   # both set → HTTPS
# tls_key  = "certs/key.pem"

[database]
path = "./data/buz.db"
max_connections = 8

[auth]
jwt_secret = ""                     # required — or set BUZ_JWT_SECRET (openssl rand -hex 32)
# Local/demo with a weak template secret only: BUZ_ALLOW_INSECURE_JWT=1
jwt_ttl_hours = 24
runner_register_token_ttl_hours = 24

[runner]
heartbeat_timeout_seconds = 90

[pipeline]
yaml_scan_dir = "./pipelines"
# Pipeline YAML files are scanned flat; the default plugin index is ./pipelines/plugins
yaml_scan_interval_seconds = 30

# [plugin_index] — OPTIONAL: every key has a default, and all three are also
# editable in the dashboard (Settings), where the DB value wins over this file.
# Most deployments register remote Step Sources in the UI instead of setting
# anything here; the section matters for air-gapped / local-mirror setups.
# [plugin_index]
# Local plugin specs used to resolve `uses:` references. Empty (default) →
# <data_dir>/plugins (e.g. ./data/plugins). Manager reads this directory; it
# does not clone/sync it.
# For a Docker Git mirror, use deploy/docker-compose.plugins.yml and set
# BUZ_PLUGIN_MIRROR to the host-side buz-plugins/plugins directory.
# local_dir = "/srv/buz-plugin-mirror/plugins"
# Index signature (optional): with require_signed_index = true every sync
# verifies index.json.sig against this public key (from `buz-plugin keygen`).
# It also turns on rollback protection: the signed `sequence` in index.json
# must not go backwards, so a replayed older (validly signed) catalog is
# refused. A fetched reviews.json must carry a verifying reviews.json.sig too.
# Sources must publish an index generated by buz-plugin 1.12+ (or
# scripts/gen_index.py from that release); mirrors must serve the same bytes.
# index_public_key = "<base64 ed25519 public key>"
# require_signed_index = false
# Review gate — RECOMMENDED for production. Without it every `uses:` plugin
# resolves unreviewed (the dashboard shows a banner and the editor warns):
# reviewed_manifest = "/etc/buz/reviews.json"   # from a catalog snapshot / the marketplace site
# require_reviewed = true    # strict: reject plugins absent from the manifest

# Dev / single-container only — leave disabled in production (default)
# [standalone]
# enabled = true
# auto_approve = ["standalone-runner"]

[logging]
level = "info"                 # error | warn | info | debug | trace
# file = "./logs/manager.log"  # optional; when set → stdout + file
```

| Section | Key | Notes |
|---------|-----|-------|
| `server` | `host` / `port` | Listen address |
| (top level) | `marketplace_url` | Public plugin-marketplace URL shown in the Dashboard's YAML editor. Default: the public marketplace; override for internal mirrors / air-gapped deployments. Env: `BUZ_MARKETPLACE_URL` |
| `server` | `tls_cert` + `tls_key` | Optional HTTPS (both required). See [TLS](/docs/03-operations/tls/) |
| `database` | `path` | SQLite file |
| `auth` | `jwt_secret` | Signs JWTs + encrypts secrets/hosts. **Required** (≥ 32 chars). Empty / `CHANGE_ME` / `changeme` / `demo-only` placeholders are **refused at startup** unless `BUZ_ALLOW_INSECURE_JWT=1` (local only) |
| `auth` | `jwt_ttl_hours` | UI/API JWT lifetime |
| `auth` | `runner_register_token_ttl_hours` | Runner JWT lifetime after register |
| env `BUZ_JWT_SECRET` | — | Overrides `auth.jwt_secret` (same key derivation); takes precedence over the config file |
| env `BUZ_HTTP_NO_SYSTEM_PROXY` | — | Set (any value except `0`) to skip the OS-level proxy probe in outbound HTTP clients and honor proxy environment variables explicitly (`http_proxy`/`https_proxy`/`all_proxy`/`no_proxy`). On macOS the default probe can stall seconds per process. See `.cargo/config.toml` for the workspace default |
| `runner` | `heartbeat_timeout_seconds` | Offline threshold for runners |
| `pipeline` | `yaml_scan_*` | File/Git authority for pipeline YAML; scanner + UI online edit write here. **Flat directory only** (basename files; no private subdirs). See [YAML-First Authoring](/docs/01-architecture/authoring/yaml-first-authoring/) |
| `plugin_index` | `local_dir` | Local plugin specs used to resolve `uses:` references. Empty (the default) uses `<data_dir>/plugins`; Manager reads the selected directory and does not clone or sync it. |
| `standalone` | `enabled` | Default `false`. When `true`, allow **loopback** Runner register without `register_token` for names in `auto_approve` (or pre-created in UI). Non-loopback register is **rejected**. Dev / `buz-standalone` only — see [Standalone mode](#standalone-mode) |
| `standalone` | `auto_approve` | Runner names created at Manager boot if missing. Default `["standalone-runner"]` |
| `logging` | `level` | Default `info`. Overridden by `RUST_LOG` if set |
| `logging` | `file` | Optional append path; empty = stdout only |

## External plugin Git mirror

Manager resolves Pipeline `uses:` references from local YAML specs; it does not
fetch the public marketplace or synchronize Git repositories. For Docker, keep a
checkout of your internal `buz-plugins` mirror on the host and mount its `plugins/`
subdirectory read-only with the optional Compose overlay:

```bash
git clone https://git.example.internal/platform/buz-plugins.git /srv/buz-plugin-mirror
export BUZ_PLUGIN_MIRROR=/srv/buz-plugin-mirror/plugins
docker compose -f docker-compose.yml -f deploy/docker-compose.plugins.yml up -d manager
docker compose exec manager /app/buz/buz-plugin validate /app/buz/plugins
```

After the mirror is updated, validate the specs again; the bind mount exposes the
updated files to Manager without adding an in-Manager sync service:

```bash
git -C /srv/buz-plugin-mirror pull --ff-only
# The review ledger must cover every version the index advertises — a stale
# reviews.json makes require_reviewed reject versions the mirror just gained.
python3 /srv/buz-plugin-mirror/scripts/check_manifest_consistency.py
docker compose exec manager /app/buz/buz-plugin validate /app/buz/plugins
```

The overlay sets `BUZ_PLUGIN_INDEX__LOCAL_DIR=/app/buz/plugins`. Set
`BUZ_PLUGIN_MIRROR` to the host-side `plugins/` directory, not the repository
root. Pipeline pins are resolved and locked when saved, so mirror changes apply
to newly saved pipelines and do not rewrite existing ones. Without the overlay,
the default is `<data_dir>/plugins` (typically `./data/plugins`); a legacy
`<yaml_scan_dir>/plugins` directory is migrated on startup.

{{< callout type="warning" >}}
**A plain `git clone` of the plugin repo can lag the deployed marketplace.**
The generated manifests (`index.json`, `reviews.json`, `revision.json`) are
written back to the repository by CI, but that push is best-effort and can be
blocked by branch protection — the deployed site is always the current one.
For an air-gapped mirror, prefer a catalog snapshot tag / the site's
`plugins/` manifest set over `master`, and run
`scripts/check_manifest_consistency.py` after every update. Under
`require_reviewed`, a version present in `index.json` but missing from
`reviews.json` is rejected at resolve time.
{{< /callout >}}

**First admin:** not in config. On a fresh database, open the UI — you are redirected to `/setup` to create the platform admin (password ≥ 8 chars, complexity rules apply). After that, use `/login`.

**Password storage:** login passwords use **Argon2id** in `users.password_hash`. This is separate from Secrets/Hosts **AES-256-GCM** encryption. A login failure is almost always a wrong password (or wrong username), not a crypto mismatch.

**Forgot admin password (local/dev recovery):** stop Manager, then from a machine with the Argon2 tooling available set a new hash, e.g. generate one via a one-liner and:

```sql
UPDATE users SET password_hash = '<argon2id-phc-string>' WHERE username = 'admin';
```

Then restart Manager and sign in. Prefer changing the password again from the UI after recovery.

## Runner (`conf/runner.toml`)

Machine-local only. Strategy is **not** configured here — see [Runner Policy](/docs/01-architecture/execution/runner-policy/).

| Managed in UI | Kept in TOML (`[runner]` / `[engine]` / `[logging]`) |
|---------------|-----------------------------------------------------|
| `labels` | `manager_url`, `register_token`, `tls_skip_verify`, `standalone` |
| `max_concurrent_jobs`, cleanup | `name`, `workspace_dir`, `token_cache_path` |
| engine enable flags + `ssh_host_key_policy` + `execution_mode` | `prefer_interfaces`, `ssh_known_hosts_path`, `docker_config_isolation`, `[sandbox]` runtime paths/images |

```toml
[runner]
name = "prod-runner-01"              # must match UI Runner name
manager_url = "https://buz-api.example.com"
register_token = "paste-from-ui"     # or env BUZ_REGISTER_TOKEN
# standalone = false                 # true → allow empty register_token (lab image only)
# tls_skip_verify = false
workspace_dir = "/tmp/buz-runner"
token_cache_path = "./state/runner-token" # durable Manager-issued JWT cache
# prefer_interfaces = ["enp26s0"]

[engine]
# ssh_known_hosts_path = "/home/runner/.ssh/known_hosts"
# Scope the Docker CLI config (docker login credentials) to the job workspace:
# "per_job" (default) → {workspace}/{job}/.docker (0700), removed when the job
# ends (success / failure / cancel). "shared" → legacy host-global
# ~/.docker/config.json (for credential-store-based setups).
# docker_config_isolation = "per_job"

[sandbox]
# Host-local wiring only (used when Manager UI → Runners selects a sandboxed
# tier). WHAT runs — tier images, OCI runtimes, resource profiles — is
# Manager-managed per sandbox host; see "Sandbox host configuration" below.
supervisor_socket = "/run/buz-sandboxd/sandboxd.sock"
workspace_root = "/app/buz/workspace"
# snapshot_path = "./state/sandboxd.snapshot.json"   # observational copy of the applied document

[logging]
level = "info"
# file = "./logs/runner.log"   # Runner default if omitted: ./logs/runner.log
```

The supervisor actively probes every configured sandboxed tier at startup and every five minutes by creating, starting, executing in, and removing a short-lived digest-pinned image — independent of the tier currently selected for the Runner, so switching tiers never waits for a first probe. Capability results, failure reasons, and the delivering OCI runtime name are reported on heartbeat and displayed in Runner details. Tier prerequisites: Container needs a Docker daemon; Sandbox needs Linux and a userspace-kernel OCI runtime (e.g. `runsc`) but no `/dev/kvm`; VM requires Linux, readable `/dev/kvm`, and a successfully exercised Firecracker-compatible OCI runtime — this is host-provided runtime delegation, not Buz-managed Firecracker/jailer. The Manager allows selecting a sandboxed tier only when the Runner is online and its capability check is no older than five minutes. A real job re-checks the tier prerequisites at start and fails closed if the host drifted after the probe; the system never auto-selects, upgrades, or downgrades the tier — that is the operator's choice in the Manager UI.

## Sandbox host configuration

The host-side `buz-sandboxd` supervisor has **no config file**. It takes only host bootstrap from
flags/environment and pulls its **policy** — resource profiles, tier images and OCI runtimes, job
network — from the Manager over HTTPS with a per-instance token. The Manager is the single source
of truth; sandboxd validates each document, applies it atomically, and caches the last good one
root-owned so it can serve jobs through a Manager outage. Until a document has been applied,
`create_job` is refused while `--healthcheck` keeps passing (there is no built-in default image or
envelope). Design record: [Sandbox Host Configuration & Resource Profiles](/docs/01-architecture/execution/sandbox-host-configuration/).

### Bootstrap (env / flags)

| Variable | Default | Purpose |
|----------|---------|---------|
| `BUZ_MANAGER_URL` | — | Manager base URL. Empty = offline: cache only, no updates. |
| `BUZ_MANAGER_INSTANCE_ID` | — | Pin the owning control plane (`GET /api/v1/meta`); a response from another Manager is rejected. Recommended in production. |
| `BUZ_SANDBOXD_TOKEN_FILE` | — | File (`0400`) holding the enrollment token (`buzsd_…`). Preferred over `BUZ_SANDBOXD_TOKEN`. |
| `BUZ_HOST_ID` | machine-id → hostname | Host identity shared with the Runner on this machine. Set it explicitly in containers/VM templates (clones share machine-ids). |
| `BUZ_RUNNER_ID` | — | Pin the Runner to a pre-declared runner row (IaC / batch registration). A mismatch with the row rejects the registration instead of binding to another. Correlation only — not an auth credential. |
| `BUZ_SANDBOXD_INSTANCE_ID` | `sandboxd-<host_id>` | Unique per Docker daemon; labels containers for stale cleanup. |
| `BUZ_SANDBOXD_SOCKET` | `/run/buz-sandboxd/sandboxd.sock` | Unix socket the Runner connects to. |
| `BUZ_SANDBOXD_WORKSPACE_ROOT` / `_WORKSPACE_VOLUME` | `/var/lib/buz/workspaces` / — | Job workspace root; the named volume in Compose. |
| `BUZ_SANDBOXD_ALLOWED_RUNNER_UID` / `_SOCKET_GID` | — / `10001` | Only this UID may connect; socket group. |
| `BUZ_SANDBOXD_DOCKER_CLI` | `/usr/bin/docker` | Docker CLI used to drive the daemon. |
| `BUZ_SANDBOXD_STATE_DIR` | `/var/lib/buz-sandboxd` | Root-owned last-known-good cache. |
| `BUZ_SANDBOXD_TLS_SKIP_VERIFY` | `false` | Labs only. |

### Enroll and publish

1. **Enroll** the `(host_id, instance_id)` pair (ops or admin): `POST /api/v1/ops/sandbox-hosts`
   or Dashboard → Sandbox Hosts → Enroll. The response shows the token **once**; store it in the
   token file on the host. Re-enrolling or `POST …/token/rotate` replaces it.
2. **Publish a document** (`PUT /api/v1/ops/sandbox-hosts/{host_id}/{instance_id}/config`,
   `If-Match: <desired_version>`), or edit it in the Dashboard. `default` must exist; every profile
   has `memory`, `cpu`, `pids`, `slots`; tier images must be digest-pinned. `POST …/validate` dry-runs.

   ```json
   {
     "profiles": {
       "default": { "memory": "2g", "cpu": "2", "pids": 256, "slots": 1 },
       "large":   { "memory": "8g", "cpu": "4", "pids": 512, "slots": 4 }
     },
     "tiers": {
       "container": { "image": "docker.io/library/debian@sha256:<digest>", "runtime": "" },
       "sandbox":   { "image": "docker.io/library/debian@sha256:<digest>", "runtime": "runsc" },
       "vm":        { "image": "docker.io/library/debian@sha256:<digest>", "runtime": "<firecracker-compatible runtime>" }
     },
     "network": "bridge"
   }
   ```
3. **Watch it apply**: sandboxd long-polls (`Prefer: wait=30`) and applies within about a second;
   `applied_version` on the host record (and the Runner heartbeat's `sandboxd` block) confirms it.
   Running containers keep the limits they were created with; new containers use the new document.
4. **Grant profiles**: `default` is implicit for every team. Grant others with
   `PUT /api/v1/ops/resource-grants {team_id, profile}`. Pipelines request one with
   `runner.resources: large`; an ungranted request fails at trigger, and a grant revoked while a job
   is queued fails that job at claim.

Capacity is two gates: `max_concurrent_jobs` per Runner (job count) and `max_resource_slots` per
sandbox host (summed over running jobs across every Runner on that host). A `large` job with
`slots = 4` consumes four units. Each Runner walks its queue by `claim_strategy`: `backfill`
(default) skips jobs that do not fit; `fifo` claims nothing while the oldest eligible job does not
fit. Pending jobs show *why* they wait (`dispatch_reason`).

Both knobs only change behavior when jobs actually wait for resource slots: with only the
`default` profile (one slot each) and unlimited host budget, the two strategies are equivalent and
starvation aging never fires. See
[Scheduling Precedence](/docs/01-architecture/execution/scheduling-precedence/) for how this gate
interacts with pipeline and environment concurrency.

Platform settings: `sandbox_config_require_approval` (two-person approval, default off),
`sandbox_config_history_retention_days` (30), `sandbox_config_poll_seconds` (30),
`sandbox_config_dispatch_stale_after_seconds` (300 — a host lagging the desired version longer than
this stops receiving non-default profiles).

### Migrating from `sandboxd.toml`

This is a coordinated, breaking release: upgrade Manager, Runner, and sandboxd binaries together
(drain jobs first). Then, per host:

1. Enroll the host and save the token file.
2. Translate the old file: `container_image`/`container_runtime` → `tiers.container`,
   `sandbox_*` → `tiers.sandbox`, `firecracker_*` → `tiers.vm`, `container_network` → `network`,
   `memory_limit`/`cpu_limit` → `profiles.default` (add `pids: 256`, `slots: 1`). Publish it.
3. Replace `--config conf/sandboxd.toml` with the bootstrap env above (Compose:
   `BUZ_MANAGER_URL`, `BUZ_SANDBOXD_TOKEN_HOST_PATH`, `BUZ_HOST_ID`, `BUZ_SANDBOXD_INSTANCE_ID`);
   delete the file. `runner.toml → [sandbox]` tier keys are ignored on load and can be removed.
4. Set `max_resource_slots` on the host record once you want slot-aware dispatch; `0` leaves the
   budget unlimited (default-profile behavior is unchanged).

`BUZ_SANDBOXD_INSTANCE_ID` must be unique per Docker daemon. On startup sandboxd refuses to take over a socket whose live peer answers a `health` probe, removes stale sockets only when nothing is listening, and force-removes leftover `buz.sandboxd.managed=true` containers carrying its own `buz.sandboxd.instance=<id>` label — it never touches other instances' containers. Compose exposes `/dev/kvm` to sandboxd only through the optional `docker-compose.vm.yml` override (`docker compose -f docker/docker-compose.yml -f docker/docker-compose.vm.yml --profile sandbox up -d`), because the default Compose path cannot reach the host KVM device. The container image ships a `buz-sandboxd --healthcheck` subcommand used as the Compose healthcheck; the Runner waits for it via an optional `depends_on` condition, so Host-only deployments are unaffected.

All sandboxed tiers currently support local shell steps only: SSH, per-step Docker engine, and host-side config preparation are rejected before the job starts. See [Runner Policy — Job-wide execution modes](/docs/01-architecture/execution/runner-policy/#job-wide-execution-modes) for the full compatibility/security boundary and [Sandbox Isolation Tiers](/docs/01-architecture/execution/sandbox-isolation-tiers/) for the tier model.

| Key | Notes |
|-----|-------|
| `register_token` | Required unless `standalone = true` (see [Standalone mode](#standalone-mode)) |
| `standalone` | Default `false`. When `true`, Runner may start with an empty `register_token` and register over loopback against a Manager with `[standalone] enabled = true` |
| `token_cache_path` | Default `./state/runner-token`. Writable, durable path for the Manager-issued JWT; created with Unix mode `0600`. `BUZ__RUNNER__TOKEN_CACHE_PATH` overrides it. The old `<workspace_dir>/runner-token` is read only when the new path is missing and removed after a successful cache write. |

> Obsolete `[manager]` section is **rejected** at startup with a migration hint. A legacy `[clock]` section is ignored (harmless).

## Standalone mode

**Dev / lab only** — same-container Manager + Runner (`buz-standalone` image), or a local loopback pair. Do **not** enable on a production multi-runner control plane.

### Manager — `[standalone]`

```toml
[standalone]
enabled = true
auto_approve = ["standalone-runner"]   # created at boot if missing
```

| Behavior | Detail |
|----------|--------|
| Boot | For each name in `auto_approve`, create an authorized runner row if absent (`labels` include `standalone`) |
| Register (loopback) | Peer `127.0.0.1` / `::1` may register **without** `register_token` when the runner name is authorized (`auto_approve` or UI **New Runner**) |
| Register (remote) | Always **rejected** while `enabled = true` — even with a valid token |
| Default | `enabled = false` — normal token registration only |

Checked-in template: `deploy/conf/manager.standalone.toml`.

### Runner — `[runner].standalone`

```toml
[runner]
name = "standalone-runner"           # must match auto_approve / UI name
manager_url = "http://127.0.0.1:8080"
standalone = true
register_token = ""                  # allowed when standalone = true
```

| Behavior | Detail |
|----------|--------|
| Startup | Empty `register_token` is allowed only when `standalone = true`; otherwise Manager refuses to start the process |
| Pairing | Expects Manager `[standalone] enabled = true` and loopback `manager_url` |

Checked-in template: `deploy/conf/runner.standalone.toml`.

First-run Compose, volumes, and upgrade: **[Standalone (single image)](/docs/03-operations/standalone/)**.

## Clocks

**Keep every host clock synchronized (NTP): the Manager and every Runner.** Job
logs, heartbeats, cron schedules and audit timestamps all compare timestamps
across hosts — a drifted clock shows up as off-timeline logs and misfiring
cron triggers. Neither process ever changes the system clock itself.

```bash
sudo timedatectl set-ntp true
sudo systemctl enable --now systemd-timesyncd   # or: systemctl restart chrony && chronyc makestep
timedatectl status                              # System clock synchronized: yes
```

> Note: the former `[clock]` config sections (Manager URL-signing probe,
> Runner skew guard) were removed in the 2.x retirement together with the kernel
> `config.source` delivery. A leftover `[clock]` section in a TOML file is
> ignored.

## Logging

| Destination | Behavior |
|-------------|----------|
| stdout | Always on (Docker: `docker logs`) |
| Runner file | **Default** `./logs/runner.log` (Docker WORKDIR → `/app/buz/logs/runner.log`) |
| Manager file | Optional via `logging.file` (no default file) |
| Level | `logging.level` (default `info`); `RUST_LOG` overrides |

Set `logging.file = ""` (or `"-"` / `"none"`) on Runner for **stdout-only**.

Examples:

```bash
# Config file
# [logging]
# level = "debug"
# file = "/app/buz/logs/manager.log"

# One-shot override
RUST_LOG=buz_manager=debug,sqlx=warn ./buz-manager -c conf/manager.toml
```

Do **not** log secrets (`register_token`, JWT, passwords). Create-runner API returns the token once in the JSON body; process logs only record name/id.

## Environment overrides

| Variable | Effect |
|----------|--------|
| `BUZ_JWT_SECRET` | Overrides `auth.jwt_secret` (required for packaged/Docker deploys) |
| `BUZ_ALLOW_INSECURE_JWT` | `1` / `true` — allow empty or placeholder JWT secrets (**local/demo only**) |
| `BUZ_MANAGER_URL` | Overrides `runner.manager_url` |
| `BUZ_REGISTER_TOKEN` | Overrides `runner.register_token` |
| `BUZ__RUNNER__TOKEN_CACHE_PATH` | Overrides `runner.token_cache_path` |
| `RUST_LOG` | Overrides `logging.level` filter |
| `BUZ__…` | Nested TOML via `config` crate (`BUZ__SERVER__PORT=8081`) |

Priority: CLI args > environment > config file > defaults.

> There is **no** `env.VAR_NAME` interpolation inside TOML strings. Use the variables above (or `BUZ__` nested keys).
